# Cash-first payment and reviewed technician responsibility — backend contract

Status: owner-approved behavior, implementation/release contract for backend base `266b709` (2026-10-29). This file distinguishes existing source from the additive contract. No migration or shared database write is implied by writing this contract.

## Source audit and invariants

| Concern | Existing source evidence | Constraint for this change |
| --- | --- | --- |
| Solo cash | `FinanceService.declareCashSettlement` creates/overwrites `CashSettlement` after technician declaration; `confirmCashSettlement` marks it confirmed only after customer confirmation (`src/modules/finance/finance.service.ts`). `cash_settlements.service_order_id` is unique. | Reverse the actors: customer intent is durable first; only assigned technician's exact physical receipt may invoke paid finalization. A historical declaration without a linked intent is not a new intent. |
| VisitGroup cash | `declareVisitCash` freezes `VisitGroupPayment.allocations`; `confirmVisitCash` creates one `CashSettlement` per billable invoice then calls `applyConfirmedCash`. `loadVisitCharge` excludes failed, quote-declined and cancelled children and requires all children to finish (`src/modules/finance/visit-charge.ts`). | One intent and one receipt for the parent. Never expose a per-child cash payment. Recheck the frozen split and current assignment for every billable child; siblings remain independent operationally. |
| Finalization | `applyConfirmedCash` writes invoice/order paid, uses `ServiceOrderStateMachine` for eligible completion, creates the cash `Payment`, snapshots `CommissionDue`/`PlatformDue`, then calls `SettlementService.trySettleOrder`. | Call this existing core inside the same receipt transaction; do not duplicate commission, wallet, dues or customer-wallet debit. Intent alone writes none of them. Completion holds remain effective. |
| F4 funding | `quoteVoucherRail` locks campaign then reservation and validates live RESERVED state, expiry and frozen invoices; `allocateFundedVisitCharge` splits **customer NET**. `commitConfirmedCashVoucherFunding` credits the subsidy to technician wallet and checks gross invoice, original PlatformDue, cash amount and timestamps (`src/modules/vouchers/voucher-funding-lock.ts`, `voucher-cash-credit.ts`). | A receipt collects only `customerDueVnd`; invoice and PlatformDue retain original gross. Bind a CASH link, finalize through existing core, commit F4 subsidy and redeem reservation in one transaction. No fake gross cash receipt or cash refund. |
| Other rails | Wallet verifies in the debit transaction; VNPay verifies by signed IPN/querydr. `payments` and `visit_group_payments` retain attempts, including unresolved provider attempts. `assertLegacyCollectionAllowed` refuses a RESERVED voucher for gross rails. | New cash must fail closed while any VNPay attempt for the scope is unresolved; it must never cancel an unresolved provider attempt. Existing attempts block intent creation and receipt; after intent creation, new wallet/VNPay attempts are blocked until cancellation. Provider callbacks remain authoritative for previously signed attempts. |
| Quote/holds | Invoice is a snapshot after approved quote and completion request. `isCompletionHeld` blocks order completion; `readyVisitCharge` requires a settled parent allocation. Zero invoices use `POST /invoices/:id/no-charge` or funded zero closeout. | No client `quoteVersion` is authoritative: freeze invoice IDs, gross/NET split and voucher reservation in the intent, then compare under locks on receipt. Positive due only; zero due uses existing routes. Hold/dispute or repricing blocks receipt. |
| Incidents | `SupportCasesService.openCaseForActor` checks owner/active assignment and allowed type; `TECHNICIAN_REPLACEMENT` needs valid check-in. `reportRepairFailed` closes a genuinely failed child at 0 VND and opens a `MID_JOB_INTERRUPTION` case. `ReputationService.penalize` skips **every** technician-created `technician_replacement` case; generic `adjust` has no case linkage. | A report itself neither changes points nor order/finance. Responsibility is determined by SM separately from operational replace/repair-failure/rebook/cancellation. Existing unrelated pre-check-in cancellation rules and group siblings remain unchanged. |

The prior plan's proposed `quoteVersion` has no authoritative invoice counterpart. Use a server-frozen allocation snapshot and current invoice locks instead. Its proposed `PENDING_SM_REVIEW` is a decision state, not a new `SupportCaseStatus`; keep `OPEN/IN_REVIEW` for workflow and add explicit responsibility fields. Old `confirmed_by_customer_id` and customer-confirm routes describe the former cash sequence; a new receipt must use the linked customer intent as its authorization, not treat an old declaration as proof of intent. The unconditional `technician_replacement` points waiver is superseded only for an audited case-linked SM fault decision, never by ordinary cancellation.

## Phase A: additive storage and HTTP contract

Add `cash_payment_intents` with UUID primary key; `scope_kind` (`SOLO`/`VISIT_GROUP`), `scope_id`, `customer_id`, `technician_id`, `status` (`pending`, `cancelled`, `received`), frozen `gross_vnd`, `customer_due_vnd`, `allocation_snapshot` JSONB of `{invoiceId,serviceOrderId,originalGrossVnd,customerDueVnd}`, optional `voucher_reservation_id`, `command_id` UUID, `created_at`, `updated_at`, `received_at`, `receipt_command_id`, receipt evidence/amount and the linked legacy settlement/payment ID. Unique `(customer_id, command_id)`, partial unique `(scope_kind, scope_id) WHERE status='pending'`, and unique technician receipt command when present. The service only updates a pending intent once into `cancelled` or `received`; database constraints enforce receipt completeness. Foreign keys use `RESTRICT` where records are financial evidence. Enable PostgreSQL RLS on this public-schema table, with no client policies; revoke table privileges from `anon`, `authenticated`, and `service_role` where those roles exist, while verifying the backend's separate DB role can still read/write. The API must mask unrelated scope and intent IDs with the existing ownership error shape, not return evidence or another customer's intent. Migration is forward-only and **does not backfill or reinterpret** old `cash_settlements`/`visit_group_payments`. An old pending cash declaration without intent remains historical and blocks new cash until staff reconciliation; never infer customer intent from it.

All paths are under `/api/v1/finance/cash-intents`; normal response uses the existing `{data: ...}` envelope and `Cache-Control: no-store`. The authenticated, ownership-checked GET additionally returns `meta.cashFirstEnabled: boolean` in the global response envelope. Exact wire shape when inactive and no intent: `{success:true,statusCode:200,message:"Success",data:null,meta:{cashFirstEnabled:false}}`; when active and no intent, only that boolean changes to `true`. Do not infer activation from `data:null`, and do not show a cash-first action when GET fails or `meta.cashFirstEnabled` is absent. The flag is informational; mutations still validate it server-side. Other scopes receive the existing ownership denial, without a capability or intent ID.

| Method/path | Actor/permission | Body | Effect/response |
| --- | --- | --- | --- |
| `GET /:scopeKind/:scopeId` | Owner customer, current assigned technician, SM/Admin (`order:read_related`) | — | Latest pending/received intent or `null`, with `id`, scope, exact due, gross, assigned technician, status, timestamps and `receiptId` after receipt; no raw allocation rows or private evidence. |
| `POST /:scopeKind/:scopeId` | Customer + `invoice:pay_own`, exact Booking/VisitGroup owner | `{commandId: UUID, voucherReservationId?: UUID}` | Atomically validate all finished billable work, positive server due, invoice/quote/hold, current active assignment, no prior cash declaration/payment or unresolved provider attempt; freeze amount/allocation/technician/reservation. Same command and payload returns same intent; conflicting command or changed payload returns 409. **No PAID, Payment, settlement or subsidy write.** |
| `POST /:scopeKind/:scopeId/cancel` | Same customer + `invoice:pay_own` | `{intentId: UUID, commandId: UUID}` | Cancel only an unreceived pending intent under the scope lock; retry is idempotent. Does not cancel a provider attempt, refund or change an invoice. |
| `POST /:scopeKind/:scopeId/received` | Current assigned technician + `order:update_status` | `{intentId: UUID, commandId: UUID, receivedAmountVnd: integer, receiptEvidenceUrl?: string}` | Explicit acknowledgement of **physically received** exact NET due. Under ordered locks, revalidate intent owner, actor, assignment for every billable order, invoice/quote/split, positive due, reservation/expiry, holds and payment exclusivity. Create legacy cash evidence and call existing definitive finalization once; mark intent `received` in that transaction. If already `received`, matching `receipt_command_id`, actor and amount return the stored receipt without any write; different command/actor/amount is 409. A mismatch, dispute or unresolved provider attempt does not pay. |

`scopeKind` accepts only the two literal values; `scopeId`, intent ID, command IDs and reservation ID are UUID v4, unknown body fields rejected by global `ValidationPipe`. The server computes every amount and invoice list. It returns 403/404 for wrong role or ownership, 409 for stale/conflicting financial state, 422 for invalid positive amount or explicit wrong physical amount, 503 if F4 paid rail prerequisites are unavailable. For `received`, a wrong amount must leave invoice unpaid; a separate existing `CASH_MISMATCH` support path can record a dispute but cannot mark paid. Clients must refresh GET after an uncertain network result. No third customer approval is called.

Lock order: F4 campaign → reservation → frozen invoice rows sorted by UUID → scope/order as existing funded rails; gross SOLO locks invoice before order to align with wallet, and gross VisitGroup locks parent → frozen invoices → child orders sorted by UUID → technician custody lock. Hold scope/intent locks through finalization. VNPay solo IPN locks its `Payment` before invoice; group IPN locks parent → provider attempt → invoices. Cash must **not** lock a provider-attempt row while holding invoice: inspect pending attempts after invoice locks without `FOR UPDATE` and fail closed; never convert an unresolved provider attempt to `cancelled` to force cash through. A concurrent IPN then either commits first and cash sees paid, or cash sees pending and refuses. No provider network call under DB locks. Wallet and VNPay route creation reject an active intent under the same scope/invoice lock unless customer cancels it; callback for an older verified provider attempt remains authoritative. Database unique indexes and existing unique payment/settlement keys are final backstops. No new dependency.

### Safe phased cutover

`CASH_FIRST_ENABLED` defaults to `false`. `CASH_LEGACY_COMPAT_ENABLED` also defaults to `false` and has no effect while cash-first is OFF. With both OFF, the additive migration and GET may ship while existing Web/Mobile declare/confirm routes continue to work. New customer intent and technician receipt mutations open only when cash-first is ON. Neither migration rewrites old cash/payment rows. Existing wallet/VNPay/zero rails remain with the active-intent guard. `GET /visit-groups/:id/checkout` keeps historical `pendingCash`; clients read the separate intent endpoint for the new state. Notifications after customer intent and technician receipt are neutral; intent alone never sends a paid notification.

With both flags ON in the **temporary DEV compatibility window**, old Mobile still uses technician declaration followed by customer confirmation, including funded Solo/VisitGroup cash. These routes require the original customer confirmation; they do not become a one-step paid shortcut. A legacy declaration takes the existing invoice/parent locks, then refuses a new `pending` cash intent on that scope before writing cash evidence. New intent creation refuses any prior Solo `cash_settlements` row or any prior VisitGroup cash payment; existing invoice/payment uniqueness and paid checks remain final backstops. A historical pending legacy record remains confirmable. A cancelled new intent does not strand a later valid Mobile legacy declaration: legacy confirmation blocks only a `pending` or `received` new intent, while receipt never needs or accepts a third customer confirmation. Legacy routes are available to all authenticated clients with existing RBAC because a client platform header cannot securely distinguish Mobile from Web. Web must exclusively use intent/receipt when GET reports cash-first ON. Reconcile old Mobile and historical pending declarations through the original two-party flow; do not relabel them as customer-first. Do not turn cash-first OFF while any new intent is pending: the release gate refuses that restart.

**DEV Web-first activation:** (1) Merge/deploy backend through CI with `docker-compose.part-returns.dev.yml` setting both flags `"false"`; the exact-two migration gate must pass, then verify `/health`, authenticated GET, RLS and backend DB grants. (2) Release Web dual-path UI; it reads GET for `SOLO/:serviceOrderId` and `VISIT_GROUP/:visitGroupId`, uses legacy flow only while `meta.cashFirstEnabled=false`, and is checked on both roles. (3) On disposable PostgreSQL/backend, verify Solo/VisitGroup gross and F4 NET receipt, subsidy/PlatformDue, old Mobile declaration/confirmation, historical pending cash and simultaneous VNPay IPN/wallet/receipt attempts; unresolved provider attempts remain reconciliation items. (4) In a separate reviewed **DEV-only overlay commit**, change both flags to `"true"`. CI derives the one-off `CASH_FIRST_DEV_ACTIVATION=1` only from that committed overlay, reruns the schema gate, and replaces Backend only on success. Verify the live flags, `/health`, Web intent/receipt and Mobile legacy declare/confirm. Subsequent DEV deploys with the overlay still ON are allowed; an overlay downgrade while a running backend is ON is blocked. Web cash-first can be demonstrated on shared DEV only after these checks; before then use isolated preview. If either role fails, preserve the running backend and reconcile new pending intents before any rollback to legacy mode.

**Retirement:** When Mobile's customer/technician screens have moved to the same intent/receipt contract, old pending cash is reconciled, and both clients have been verified, set `CASH_LEGACY_COMPAT_ENABLED=false` in a reviewed release. That closes new legacy declaration writes while retaining customer confirmation for historical, intent-less `PENDING_CONFIRMATION` records until they are fully reconciled. Removing the legacy routes is a later separate change. No shared DEV activation or migration is performed by this task.

## Phase B: typed report and one decision

Reuse `support_cases` as the record. Add nullable `reason_class` (`technician_skill_gap`/`non_technician_exception`), `reason_code` (`skill_gap`, `device_too_old`, `severe_damage`, `no_compatible_part`, `manufacturer_warranty_or_workshop`, `customer_absent`, `customer_cancelled`, `dispute_or_other`), and `responsibility` (`pending_sm_review`, `technician_fault`, `no_technician_fault`, `inconclusive`) with decision actor, reason, evidence and time. These fields are null for historical/unrelated cases. Add `reputation_events.support_case_id` with a unique partial index for one sanction event per case; retain event's actor, delta, points after and reason. Additive migration only; no retroactive penalty.

`POST /api/v1/support/cases/technician-report` requires JWT technician, `order:read_related`, `{serviceOrderId, reasonClass, reasonCode, reason, evidenceRefs?}`. Reason is trimmed, bounded and mandatory; code/class pairing is strict. The service checks active assignment, valid check-in and `EN_ROUTE`/`UNDER_REPAIR`, creates one urgent typed SupportCase under order lock and notifies SM/Admin and customer neutrally. Repeated open report for same order/reporter remains the same pending case; changed reason needs an explicit new review rather than silently overwriting evidence. The operation changes neither points nor invoice/order state. Group child reports do not close siblings.

`POST /api/v1/support/cases/:id/responsibility` requires JWT SM/Admin with `support:resolve`, `{commandId: UUID, workflowVersion: integer, decision: 'technician_fault'|'no_technician_fault'|'inconclusive', reason: nonblank, evidenceRefs?}`. Lock case then technician User; verify typed report, actor and version. A matching replay returns the recorded decision; a conflicting replay/version returns 409. For `technician_fault` only, use configured `reputation.violation_points`, existing clamp/threshold/penalty rules, and insert **one** linked `ReputationEvent` with manager actor, before/after points, case ID and rationale in the same transaction. No-fault/inconclusive writes no point event. Audit includes actor, decision, evidence and score change. The operational outcome remains a separate existing manager interruption/repair-failure/rebook/cancellation command; determining fault never implies a repair failure or cancellation. Legacy untyped cases cannot be sanctioned through this endpoint. The old automatic waiver remains for cancellation when a technician filed an exception; the case-linked SM sanction is an explicit separate path. Notifications must describe review outcome rather than promise unconditional immunity.

## Verification and release gate

RED-first unit tests cover owner/RBAC, positive due and zero route, stale quote/allocation, pending provider, duplicate intent/receipt, current assignment, funded gross/NET/subsidy and group failed child, legacy coexistence and points decision race/replay/one event. Disposable PostgreSQL migration and concurrent HTTP tests are required before enabling collection on shared infrastructure; no test may write the shared DEV database. F3 wallet-only refund source/ledger and old migration history must remain unchanged. Run `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`; PostgreSQL E2E and Docker `/health` only in an isolated environment. Review SQL lock order, unique indexes, RLS and both consumer contracts. Release is blocked if a new cash-intent path marks paid without customer intent plus current technician receipt, a legacy path marks paid without its original customer confirmation, either path overlaps on one scope, a provider-confirmed payment is lost, funded cash collects gross, subsidy/dues/points duplicate, or a typed report becomes automatic repair failure.

DEV CI release gate: `src/database/cash-reputation-dev-release.ts` runs only with `NODE_ENV=production` and `CASH_REPUTATION_DEV_RELEASE=1`; an ON cash-first flag additionally requires `CASH_LEGACY_COMPAT_ENABLED=true` plus the one-off `CASH_FIRST_DEV_ACTIVATION=1` derived by CI from the committed DEV overlay. It requires the voucher Core, F4 funding, campaign lifecycle and interruption migration names already in `public.migrations`, prerequisite tables/columns and an authorized RLS-bypassing backend DB role. It accepts only the ordered suffix `CashPaymentIntents1793293200000` then `TechnicianResponsibility1793293200001`: both pending, only the second pending after an interrupted first attempt, or neither pending on retry. An ON flag is refused while either migration is pending, enforcing a prior schema-only release. Any other pending migration, missing prerequisite, inconsistent ledger, pending new intent while desired mode is legacy, missing RLS/revokes/trigger/unique indexes/columns/constraints or insufficient backend table access aborts before the running Backend container is replaced. TypeORM applies each new migration in its own transaction; a failure after the first is forward-retried, never rolled back over historical money. CI's isolated PostgreSQL test creates and drops its own database on the CI service; its prerequisite schema is a minimal fixture, so it does not prove the historical migration chain. It does not use the shared DEV DB and does not prove provider callbacks or full financial concurrency.
